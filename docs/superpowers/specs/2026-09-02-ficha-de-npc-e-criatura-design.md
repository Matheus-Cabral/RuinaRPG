# Ficha de NPC & Ficha de Criatura — MudBlazor rewrite

**Date:** 2026-09-02
**Status:** Approved (chat design accepted 2026-09-02, spec written for record)

## Context

`FichaDePersonagem.razor` finished its move from Bootstrap/`TabControl` to MudBlazor across three prior rounds (Fundação `deeb80d`, Fase 1a `613c335`, Fase 1b `9ab30bb`). `FichaDeNpc.razor` and `FichaDeCriatura.razor` are the two remaining pages still on the old stack — both are explicitly documented as diffs against Ficha de Personagem in their own Requisitos docs (`Requisitos - Ficha de NPCs.md`, `Requisitos - Ficha de Criaturas.md`), and their current code mirrors that: large stretches of both files (Combate's weapon/armor/shield lists, all of Magias & Habilidades, all of Posses) are byte-for-byte identical in structure to Personagem's pre-rewrite markup, just with `Npc`/`Creature`-prefixed contract types.

This is a **markup-only rewrite** for both pages, same discipline as every prior round: `@code` (the `Load*Async`/`Add*Async`/`Update*Async`/`Delete*Async` HTTP-calling methods) does not change except for the two fixes below, which are ports of fixes already proven correct on Personagem, not new design.

Two `@code` changes travel with the rewrite, both precedent, not invention:
1. **Nullable-int form-model fix.** Both `SheetFormModel`s still have non-nullable `int` fields for the same class of resource values Fase 1b fixed on Personagem (Nível, Experiência Atual, Núcleos de Rank ×7, Pontos de Ignição, Vitalidade/Foco/Adrenalina/Estresse Atual — NPC only has Estresse; Criatura doesn't have Núcleos de Rank or Pontos de Ignição split, it has a single `PontosDeIgnicao`, `Kill`, `Assistencia`). Left as-is, `MudNumericField T="int"` bound to these fields silently persists a cleared field as `0` instead of blocking submit — exactly the regression Fase 1b's final review caught and fixed on Personagem. Both pages get the identical treatment: `int` → `int?` + `[Required]` on each, `<DataAnnotationsValidator />` added to the Informações Básicas `EditForm`, and a `SaveAsync` guard (return + set `_errorMessage` if any required field is null) — matching Personagem's guard exactly. Neither NPC's nor Criatura's other tabs currently call `SaveAsync` from an unvalidated live-update path the way Personagem's Cobertura/Ciclos did, so this round doesn't inherit that specific cross-tab crash risk — but the new Cobertura control added below (point 2), and NPC's new Ciclos control, *do* introduce exactly that shape (a live `MudSelect`/`MudNumericField` calling `SaveAsync` directly, no validator in front), so the guard is not optional insurance here, it is load-bearing from the moment either ships.
2. **`Cobertura` UI control (both pages) and `Ciclos` UI control (NPC only).** Neither `FichaDeNpc.razor` nor `FichaDeCriatura.razor` currently renders a Cobertura control anywhere, even though both `SheetFormModel`s already carry the field and both `Update*SheetRequest`s already send it — the exact same "backend/model wired, frontend control missing" gap Épico 1 item 5 fixed on Personagem (`MudSelect` + `UpdateCoberturaAsync`, which saves then reloads Tabs 2/3 since Cobertura feeds Defesa Natural). NPC's `SheetFormModel` also carries a `Ciclos` field, also sent by `UpdateNpcSheetRequest`, also rendered nowhere — the identical gap, one field over (confirmed: `NpcSheetsController` genuinely applies it, `sheet.Ciclos = request.Ciclos` equivalent — this isn't an ignored/vestigial column). Criatura's `SheetFormModel` has no `Ciclos` field at all, so Criatura gets Cobertura only. Both discovered while reading the current files for this spec, not previously tracked in the gap-audit backlog for these two pages. Small, low-risk, directly relevant to tabs already being touched — Cobertura added to both pages' Combate tab (Sub-Atributos section) mirroring Personagem's `UpdateCoberturaAsync` exactly; NPC's Ciclos added to its Posses tab (Inventário section) mirroring Personagem's `UpdateCiclosAsync` exactly. Because both call `SaveAsync` directly and `_form` is shared page-level state, both must ship in the same task as the nullable-int guard (point 1) — never separately — so there is never a moment where either exists without the guard in front of it.

Everything else is component substitution: same transformation rules already validated three times over on Personagem (`TabControl`/`TabPage` → `MudTabs`/`MudTabPanel`, bare `<input>`/`<select>` → `MudTextField`/`MudNumericField`/`MudSelect`/`MudCheckBox`, bare `<table>` → `MudSimpleTable`, bare `<button>` → `MudButton`, `<p class="error">` → `MudAlert`, plain `<h3>`/`<ul>` groupings → `Section`).

## Scope

Two independent worktree + `subagent-driven-development` cycles, run sequentially: NPC first, then Criatura (NPC has both fields Criatura lacks — Linhagem/Vocação/SubVocação dropdowns via existing `LinhagemVarianteFields`/`VocacaoSubVocacaoFields` — plus Habilidade Racial and Runas sections in Magias & Habilidades that Criatura also lacks, so NPC is the fuller superset; doing it first means Criatura's plan can point back at proven patterns instead of the other way around). Each page is a single `@page` route, single `.razor` file, 5 tabs, no Diário tab (neither NPC nor Criatura has one per their Requisitos diffs).

**Shared components reused as-is (no changes needed to any of them):** `Section`, `Breadcrumbs`, `EntityPicker`, `AfinidadeSelect`. NPC additionally reuses `LinhagemVarianteFields`/`VocacaoSubVocacaoFields` (Criatura has neither — Raça/Sub Arquétipo stay free-text `MudTextField`, Arquétipo/Rank are small fixed-option `MudSelect`s with no cascading behavior, unlike Variante/Sub-vocação).

## Per-page task breakdown

Two tasks per page, mirroring Personagem's Fase 1a/1b split at a smaller scale (these pages have 5 tabs vs. Personagem's 6, and no Diário). Both tasks touch the same single file sequentially, never in parallel — same rule as every prior round of this rebuild.

- **Task 1 — shell open + Informações Básicas + Atributos & Perícias.** `<h1>`/error `<p>` → `MudAlert`, opening `<TabControl>` → `<MudTabs>`, Tabs 1-2's outer `TabPage` → `MudTabPanel` plus full content rewrite (Informações Básicas: identity fields, Nível e Progressão, Âmbares Absorvidos for NPC / Nível e Progressão for Criatura, Recursos; Atributos & Perícias: 2 `MudSimpleTable`s + Afinidades list for NPC only — Criatura has no Afinidades tab section, per the requirements diff), plus the nullable-int + `DataAnnotationsValidator` + `SaveAsync` guard fix. Tabs 3-5 are deliberately left **untouched** (still `<TabPage>`, still old Bootstrap content) — mixing `<TabPage>` children under an already-opened `<MudTabs>` is a real compile error (RZ1034/RZ9991/RZ9981, already hit in Fase 1a), so Task 1's own `dotnet build` is expected to fail. Say so explicitly in the task brief — don't assert an unverified clean build — and have the task reviewer independently re-run the build to confirm every error traces to the still-open Tabs 3-5, not a real defect (the same "independently rebuild to triage" discipline Fase 1a's reviewers used).
- **Task 2 — Combate + Magias & Habilidades + Posses + close the shell.** Converts Tabs 3-5's outer `TabPage` → `MudTabPanel` and closes `</TabControl>` as `</MudTabs>` — the first point in the plan where a clean build is expected — while rewriting their content: Combate (weapons/armor-slots/shields lists, identical `MudSimpleTable` shape to Personagem's Combate, already proven, plus the new Cobertura `MudSelect` + `UpdateCoberturaAsync`), Magias & Habilidades (Habilidade Racial Section for NPC only — Criatura has no Habilidade Racial per its diff doc; Runas Section for NPC only — Criatura has no Runas; both have Magias e Habilidades e Maestrias), Posses (NPC: Inventário — with the new Ciclos control + `UpdateCiclosAsync`, identical to Personagem's — /Artefatos/Afeições/Características; Criatura: Espólios/Artefatos/Afeições/Características, no Ciclos control — Criatura's `SheetFormModel` has no `Ciclos` field at all — Espólios uses the unrestricted `SearchAllItemsAsync` picker already present in the current code, not `SearchItemsByTipoAsync`).

**Criatura-specific markup not present anywhere in Personagem or NPC, called out explicitly for the Criatura plan:** the weapon add-form's Origem toggle (`MudSelect` Catalogo/Manual) with conditional manual-entry fields (Nome, Tipo de Dano select, Dados text, Dano number) for natural attacks with no catalog `ItemId`; the weapon list's per-row conditional (Durabilidade input only when `ItemId is not null`, else "Ataque natural" text) — both need to survive the `MudTextField`/`MudSelect`/`MudNumericField` swap with their `@if`/`else` structure intact, not flattened.

## Testing

- `dotnet build` (0/0) after every task — Task 1 of each page is the one documented exception (expected to fail: Tabs 3-5 stay as `<TabPage>` under an opened `<MudTabs>` until Task 2 converts and closes them).
- Final whole-branch review per page: empirical Playwright verification against the running docker stack (the pattern that has caught a genuine Critical bug in every round since Fase 1a) — serve the client from the worktree behind a proxy to the running stack, provision throwaway GM + NPC (or GM + Criatura) + campaign data via the API, drive all 5 tabs headless in both light/dark, delete the test data after. Specifically exercise the new Cobertura control (change it, confirm the save + Sub-Atributos reload round-trips) and the nullable-field guard (clear a required Tab-1 field, then trigger the Cobertura save from Tab 3 without ever submitting Tab 1 — the exact cross-tab shape Fase 1b's review caught).
- No new bUnit coverage planned for either page (same call as Fase 1a/1b — proper endpoint stubbing for `OnInitializedAsync`'s ~8-10 calls is infrastructure work disproportionate to a markup-only plan; parked as a future recommendation, not a gap introduced here).

## Known pitfalls to write directly into both plans' task briefs (not rediscover)

- `BreadcrumbItem` collision: both files build `List<BreadcrumbItem>` using the app's own type; the required `@using MudBlazor` will collide with `MudBlazor.BreadcrumbItem` exactly like it did twice on Personagem. Fix: fully-qualify `RuinaRPG.Client.Shared.BreadcrumbItem` at the two use sites (declaration + `new()` calls), don't add a bare `@using RuinaRPG.Client.Shared` that could re-trigger it.
- No `Dense="true"` on `MudNumericField` (illegal, `MUD0002`, caught mid-Fase-1a).
- `MudNumericField T="int?"` on every live-update numeric field from the start — the table cells (Gasto/Bônus/Durabilidade), not just the `EditForm`-bound fields — since these are the same shape as Personagem's already-fixed live-update fields, no reason to reintroduce the `T="int"` version even transiently.
- `EntityPicker` fields still have no visible `<label>` (relies on `Placeholder=` only) — known, matches existing precedent on Personagem's Posses tab, not this round's job to fix.
- Need `@using RuinaRPG.Client.Shared.Fields` on NPC's file (for `LinhagemVarianteFields`/`VocacaoSubVocacaoFields`) — missed initially on Personagem's Task 1 and only surfaced as a build error later; call it out up front this time.

## Process

Each page: `EnterWorktree` → `superpowers:subagent-driven-development` (implementer + task reviewer per task, final whole-branch reviewer at the end) → `superpowers:finishing-a-development-branch` decides merge/PR/keep-as-is (ask each time, don't assume "merge to main"). NPC's cycle completes (through finishing-a-development-branch) before Criatura's starts.
